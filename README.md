# DSH-Content-Hub
一份内容，多个平台，事实不漂移。把长文/访谈/报告拆成六类可复用内容原子（观点、证据、故事、步骤、引语、问题），按文章/短视频的媒介语法重新编排，并打包检查跨稿事实一致性。DSH 插件。One source, many formats, zero fact drift. Atomize long-form content into six reusable units (claim, evidence, story, step, quote, question), adapt them to article and short-video templates, and audit cross-draft consistency. A DSH plugin.

# Content Hub 使用说明书

**版本**：v1.0（验收通过版）
**定位**：把一份内容拆成可复用的事实单元，再按不同媒介的叙事语法重新编排，保证多平台分发时事实不漂移。
**概述**
Content Hub 是一个 DSH 插件，解决“一份深度内容要发多个平台，每版手动重写、还容易把数据写错”的问题。

它不直接“生成五个版本”，而是先把素材拆成可追溯来源的六类内容原子，再按目标媒介的叙事语法选取、排序、编排成稿。同一份素材生成的文章和短视频脚本，结构是真的不同；打包时还能检查同一事实在不同稿子里有没有被改错。

适合：公众号长文 + 小红书图文 + 短视频口播 + 邮件简报的多平台分发；访谈/播客/会议记录的内容提炼；团队多人改同一内容不同版本时的事实统一。

不适合：纯创意写作、单平台一次性内容、需要模仿特定文风的场景。




## 1. 它是什么

一个 DSH 插件。你给它一份素材（文章、访谈、报告、会议记录），它做三件事：

1. **拆原子**：把素材拆成六类最小信息单元——观点、证据、故事、步骤、引语、问题，每条都记录来源段落。
2. **按媒介编排**：从原子库里按目标媒介的叙事规则选取、排序，生成文章或短视频脚本。同一份素材，两种媒介的结构是真的不同。
3. **打包查一致性**：把多份渠道稿打包，检查同一事实在不同稿子里有没有被改错。

**一句话**：它省的是“一份内容改五个平台、每版手动核对数据”的时间，不是“从零创作”的时间。


## 2. 什么时候该用

### ✅ 用它的四个信号

| 信号 | 典型场景 |
|---|---|
| **一份内容要发 ≥2 个平台** | 公众号长文 + 小红书图文 + 短视频口播 + 邮件简报 |
| **素材里有可核验的事实** | 数据、调研结论、受访者原话、步骤流程 |
| **怕跨平台写错数据** | 同一组数字要在多个渠道出现，人工搬运容易出错 |
| **多人协作改同一内容的不同版本** | 编辑写长文、运营改脚本、设计做卡片，需要统一事实源 |

### ❌ 别用它的四种情况

| 情况 | 原因 | 替代做法 |
|---|---|---|
| 纯创意写作（小说、诗歌、slogan） | 原子模型是为非虚构设计的，拆原子会把灵感切碎 | 直接让 AI 写 |
| 只发一个平台、只写一版 | 走四步流程是过度工程 | 直接让 AI 写 |
| 素材是纯口语逐字稿、大量错别字、无分段 | 抽取依赖段落和句子边界，太乱会失准 | 先粗整理再喂 |
| 需要模仿某位作者的文风 | 它管事实和结构，不管笔调 | 另用文风类工具 |


## 3. 怎么用：标准四步

不需要记工具名，用自然语言说就行。

### 第 1 步：给素材，让它拆

> “用这段素材启动一个 content-hub 项目，项目名 `xxx`。先摄入，再抽取原子，抽完按类型列出来给我看。”

把文章/访谈/报告贴在后面，或给文件路径。

**建议第一次只跑到这里就停**，看一眼类型分布和两三条代表性原子。抽取质量是整个流程的天花板，这一步没看好，后面适配再漂亮也是歪的。

### 第 2 步：确认原子质量（30 秒）

只看两件事：

- **有没有哪类原子明显不该为空却空了**（比如素材里明明有带引号的原话，但引语=0）。
- **来源段落能不能指回原文位置**（每条原子应该带类似“第 2 段”的标记）。

没问题就继续。有小标题被当成观点、机构名单独成一条证据，属于正常噪声，不用管。

### 第 3 步：生成渠道稿

> “基于这个项目，生成一版公众号文章（语气 analytical）和一版短视频脚本（语气 conversational）。”

它会按媒介模板编排：文章走“导语→论点→证据→方法→收尾”，短视频走“钩子→张力→收尾”。**结构是真的不同，不是把长文截短。**

### 第 4 步：打包查一致性

> “把两份草稿打包成渠道包，看看有没有跨稿的事实不一致。”

正常应该是 0 警告。如果有警告，看它指认的是不是真实矛盾（比如同一数据在两稿里数字不同）。


## 4. 常见用法速查

| 你想做的事 | 直接说 |
|---|---|
| 只拆原子，不生成稿 | “用 extract_atoms 把这篇的证据和引语抽出来” |
| 已有原子库，只加一种新媒介 | “基于项目 xxx 的原子库，生成一版短视频脚本” |
| 检查两篇稿子事实是否一致 | “把这两份草稿打包，看 consistency_warnings” |
| 看项目进度 | “查一下项目 xxx 的状态” |
| 指定某条原子用在某段 | “文章结尾用那条讲‘可及性’的观点” |


## 5. 使用效果：诚实预期

### 做得好的

- **结构差异真实**：同一素材，文章五段位、短视频三段位，选中的原子和角色都不同。
- **事实可追溯**：每句话背后的原子都有来源段落，跨稿打包能查出谁把数据改错了。
- **降级能力可用**：数据报告没有故事，短视频钩子会自动 fallback 到生成的引导问题；分析文章证据少，文章的证据段会自动 fallback 到观点句。不会因为某类原子缺失就崩掉。

### 需要管理预期的

| 现象 | 说明 |
|---|---|
| **抽取有少量噪声** | 小标题可能被当成观点原子，机构名+年份可能单独成一条证据。拿到原子列表扫一眼，别指望 100% 干净。 |
| **适配是“按偏好选原子”，不是“通读全文重写”** | 好处是可控、可追溯；代价是原子库质量决定适配稿质量。 |
| **生成的引导问题是 AI 编的** | 标记为低置信度、来源为“生成”。可用于短视频钩子或文章收尾提问，**不要当成原文事实引用**。 |
| **它不替你做编辑判断** | 论点选哪条、钩子选哪条，是按亲和度分数排的。你觉得“这条明明更适合开头”，就直接指定。**它是助手，不是主编**。 |

### 一句话效果

> 输出不是“惊艳的原创”，是“**结构正确、事实可靠、可以在此基础上做编辑判断的初稿**”。


## 6. 已知限制（记录在案，不影响日常使用）

1. **小标题噪声**：短行小标题可能被当作观点/故事/步骤原子。适配时留意论点段和钩子段有没有选到它们。
2. **来源元数据粒度**：如“某研究院 2023 年发布的研究显示”可能单独成一条证据，占据证据段名额。
3. **同段多原子并存**：同一段可能产出语义重叠的完整观点和引语摘录，适配时按段位偏好择一使用，另一条留在库里未被使用是正常现象。


## 7. 进阶技巧

- **素材有特殊结构时，提前说一句**：“这篇第 3 部分是一个三步流程，第 2 段有一句带署名的引语。” 能让抽取更准，比事后修规则快。
- **指定原子用途**：如果适配稿选错了论点或钩子，直接说“论点用那条讲‘可及性’的”，不用改规则。
- **定期做一次破坏性验证**：手动改一份草稿里的一个数字，重新打包，确认还能报警。成本很低，能防止一致性检测静默失效。
- **扩展新媒介**：目前支持文章和短视频。要加播客口播稿或卡片系列，需要同时改 `SUPPORTED_MEDIA` 枚举和 `templates/` 下的 YAML 文件——这是唯一需要手动同步的两处。


## 8. 第一次使用的建议

挑一篇**你自己写过、知道正确结论**的文章。跑完整流程后看两件事：

1. 适配稿有没有把关键证据用错位置？
2. 有没有漏掉你认为最重要的主张？

这两项没问题，后面就可以放心用它做多平台分发。如果某项反复出问题，那才是值得调规则的地方——比拿测试素材调更有针对性。

**频率建议**：一篇内容要发 2 个以上平台时用它；单平台直接让 AI 写。它省的是“多版本一致性”的时间，不是“从零创作”的时间。
